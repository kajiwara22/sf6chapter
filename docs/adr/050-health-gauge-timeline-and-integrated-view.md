# ADR-050: ラウンド単位の体力ゲージ時系列取得と3ゲージ統合表示

## ステータス

採用 - 2026-10-10（壁打ち完了・実装待ち）

## 文脈

### 要望

SF6 の対戦動画から、**ラウンド内で体力ゲージがどう変化したか**を 1P/2P サイド別に取得し、
[docs/adr/048](048-round-drive-sa-gauge-timeline-capture.md) で実装したドライブゲージ・SAゲージと
**同じラウンド軸上で並べて**確認できるようにしたい。

- 「ラウンド間で、時系列で体力・ドライブ・SA がどう変化したか」を1画面で見たい
- 体力は連続値なので、ゲーム内の実数値（例: 10000 → 6260）でも見られると嬉しい

### ADR-048 との関係

ADR-048 で「ラウンド境界の検出」「HUD 表示判定」「変化点方式」「`gauges/{match_id}.json` と
`round_stats.parquet` への保存」「Web の詳細パネル」が揃っている。
体力はこれらと同じ枠組みに乗せられるため、**本 ADR はデータモデルと計測対象の拡張**を定義し、
ラウンド境界・保存・表示の基盤は ADR-048 を参照する。

### 実動画での実測（本 ADR の根拠）

対象: `packages/local/download/20261006[DSgD_bQhxp0].mp4`（1920x1080 / 60fps）

| 項目 | 実測値 |
|------|--------|
| 1P 体力バー | x 176〜866, y 62〜98（ドライブゲージの真上。固定座標） |
| 2P 体力バー | x 1054〜1744, y 62〜98（1P の左右ミラー） |
| 減り方 | 両サイドとも**画面中央側を残して外側から減る**（1P は右端、2P は左端を基準に塗り幅を測れる） |
| 満タン時の見た目 | 1P: マゼンタ〜赤のグラデーション / 2P: 青（シアン）のグラデーション。白い縁取りあり |
| 空き部分 | 暗色のトラック（1P: 暗い赤褐色、2P: 暗い青灰色）。背景は透けない |
| 回復可能ダメージ | 黄〜白で描画される。実測 t=100・t=115 では**内側端（現在体力より更に内側）に黄が現れた** |
| 分解能 | バー幅 約 690px → 1px ≒ 0.15%。0.1% 刻みの計測が可能 |
| 観測例（1P） | t=24: 89% → t=50: 47% → t=65: 25.8%（ROUND 1）、t=100: 62.6%（ROUND 2 でリセット） |
| 観測例（2P） | t=24: 100% → t=50: 69.3% → t=65: 72.2% → t=100: 78.8%（**回復可能ダメージの自然回復で増加**） |

この観測から、回復可能ダメージ（黄）を含めて「塗られている幅」を測ると値が自然回復で増加する。
**「現在体力」と「回復可能ダメージ」は別の情報**として扱う必要がある。

### キャラクター別の最大体力

SF6 の最大体力は 4 段階のみで、キャラクター別の表として管理できる。

| 最大体力 | キャラクター |
|---------|-------------|
| 9000 | 豪鬼（GOUKI） |
| 10500 | マリーザ（MARISA）/ E.ホンダ（E.HONDA）/ アレックス（ALEX） |
| 11000 | ザンギエフ（ZANGIEF） |
| 10000 | その他（既定値） |

出典: 第三者まとめサイト <https://game-logbook.com/street-fighter6-hp/amp/>（公式サイトの各キャラクター
フレームデータページの体力欄を集計したもの）。公式サイトは自動取得が 403 で拒否されるため、
**新キャラクター追加時は手動でこの表を更新する**運用とする。

## 決定

### 1. 記録するのは「現在体力」のみ（0〜100%、小数1桁）

- 回復可能ダメージ（黄）は記録しない。自然回復で緩やかに増減するため、変化点方式と相性が悪く、
  「体力が増えた」ように見える誤解を招くため
- 連続値のため、**変化点方式の閾値を 0.5%** として、被弾・回復による意味のある変化だけを記録する
- 体力はラウンド開始で満タン、K.O. でドレイン演出 → ADR-048 のラウンド境界・HUD 表示判定をそのまま使う

### 2. 計測は ROI 画素解析（ADR-048 と同じ枠組み）

- 各列を「現在体力の色（1P: マゼンタ〜赤 / 2P: 青）」で判定し、**その列数 ÷ バー幅** を体力％とする
  - 回復可能（黄〜白）と空きトラックは数えない
- しきい値・平滑化・短い欠損の補完は ADR-048 と同じ方式（メディアン平滑化＋欠損補完）
- ROI は 1080p 基準で `x 176〜866 / y 62〜98`（1P）、`x 1054〜1744 / y 62〜98`（2P）。
  解像度比例でスケールする（ADR-048 と同じ）

### 3. 保存は既存 `gauges/{match_id}.json` の拡張（新規ファイルを作らない）

- 各サイドに `health`（`[経過秒, 体力%]` の変化点列）と `healthCoverage`（計測率）を追加
- 既存フィールド（`drive` / `sa` / `coverage` など）はそのまま維持し、**Web 側の既存実装を壊さない**
- `coverage` は従来どおり「ドライブ計測を基準にした HUD 可視率」、体力は `healthCoverage` で別に示す

### 4. 実数値（HP）はレコードに持たず、表示時に計算する

- 記録は％のみ。`schema/character_health.json`（単一ソース）にキャラ別最大体力を持ち、
  `HP = 体力% × 最大体力 / 100` を表示時に計算する
- ローカル側は上記表を読み込み、未知キャラクターは既定 10000 として警告ログを出す
- Web 側は同じ表を参照して相対表示（例: `6260 / 10000`）を行う

### 5. `round_stats.parquet` に体力の集計列を追加

- `healthMin` / `healthAvg` / `healthEnd`（いずれも％、nullable）を追加する
- 既存行は null になる（PyArrow の nullable 列として追加するため後方互換）
- Web の `round_stats` 参照側は null 許容で扱う

### 6. Web 表示は既存の詳細パネルを拡張

- 1 ラウンド = 1 ブロックの中を **体力（0〜100%）/ ドライブ（0〜6）/ SA（0〜3）の3段** で表示する（それぞれ独立した帯として縦に並べる）
- 体力のツールチップには実数 HP（キャラ別最大体力から計算）を併記する
- 自分視点変換・データ欠損時のフォールバックは ADR-048 の実装をそのまま使う

### 7. 適用範囲は ADR-048 と同じ

- 新規動画は本線パイプライン（ADR-048 の相乗りフック）で自動計測する
- 既存動画は `scripts/analyze_gauges.py --video-id <id>` で再処理する

### 8. ADR は新規（ADR-050）として起こす

- 049 はカウンター検出（別 ADR）で使用済みのため 050 とする
- ADR-048 は「ドライブ・SA」の設計として維持し、本 ADR は「体力」と「3 系列の統合表示」を定義する

## 選択肢の比較

### 体力の定義

| 方式 | 見え方 | データ量 | 判定 |
|------|--------|---------|------|
| A. 現在体力のみ | 被弾で階段状に減少。誤解がない | 小 | **採用** |
| B. 現在＋回復可能を別系列 | 回復可能も帯で見える | 中（自然回復で変化点が増える） | 将来必要になったら追加 |
| C. 合計（回復可能込み） | 自然回復で「体力が増える」ように見える | 大 | 不採用 |

### 単位・粒度

| 方式 | 精度 | 追加データ | 判定 |
|------|------|-----------|------|
| A. 0〜100% のみ（小数1桁） | 0.15% ≒ 1px | 不要 | **採用** |
| B. 0〜100%（小数2桁） | ピクセル限界まで | 不要 | 過剰 |
| C. ％＋実数 HP をレコードに保存 | 同上 | キャラ別最大体力が必要 | レコードは冗長（表示時に計算する方針を採用） |

### 保存先

| 方式 | 影響 | 判定 |
|------|------|------|
| A. 既存 `gauges/{match_id}.json` に `health` を追加 | Web の取得は 1 ファイルのまま | **採用** |
| B. 別ファイル（`gauges/{match_id}.health.json`） | 取得が 2 回になる。ファイル数増 | 不採用 |
| C. 新規テーブル | 3 ゲージが別テーブルに分かれ、突合が面倒 | 不採用 |

## リスクと対策

| リスク | 内容 | 対策 |
|--------|------|------|
| 回復可能ダメージの解釈 | 「現在体力の内側に黄が現れる」という実測は 2 フレームのみの観測で、仕様の断定はできない | 実装時に複数ラウンドでキャリブレーションし、「現在体力色の列数」で測る。想定と異なる場合は ADR を更新 |
| ラウンド開始のフィル演出 | ラウンド開始直後はバーが満タンへ伸びる演出があり、% が一瞬低く出る | HUD 表示判定（ADR-048 の SA 数字検出）で演出中は欠損扱い。残る場合はラウンド先頭 1 秒を欠損として扱う |
| K.O. 時のドレイン演出 | K.O. 直後にバーが 0 へ向けて減る演出があり、最終値が 0 付近になる | K.O. 後の数秒は「ラウンド終端の演出」として `roundEndTime` 以降は集計から除外する |
| キャラ別最大体力表のメンテ | 新キャラクター追加や調整で表が古くなる（第三者サイト由来） | 既定 10000＋未知キャラは警告ログ。公式フレームデータページの体力欄で四半期ごとに確認 |
| 既存 JSON との後方互換 | `health` が無い過去の `gauges/{match_id}.json` が存在する | Web は `health` が無い場合「体力データなし」と表示し、例外にしない |
| `round_stats` の列追加 | 既存 Parquet に行がない列が増える | nullable で追加し、Web 側は null を許容 |
| 体力の誤検出（ステージ背景） | ステージによっては赤/青の背景がバー領域に被る | バーは白い縁取りを持ち不透明なので、ROI をバーに合わせることで背景は入らない。計測不能時は `healthCoverage` が下がるので検知できる |

## データモデル（ADR-048 からの差分）

`gauges/{match_id}.json` の各サイド:

```json
{
  "player1": {
    "visibleFrom": 0.57,
    "visibleTo": 50.3,
    "coverage": 0.958,
    "healthCoverage": 0.94,
    "health": [[0.62, 100.0], [3.14, 89.4], [7.05, 76.2]],
    "drive": [[0.57, 5.88], [3.03, 5.16]],
    "driveBurnout": [[12.03, 50.18]],
    "sa": [[0.78, 0], [22.32, 1]],
    "saProgress": [[0.78, 0.0]],
    "saCriticalArt": []
  }
}
```

- `health`: `[ラウンド開始からの経過秒, 現在体力%]` の変化点列（閾値 0.5%）
- `healthCoverage`: そのラウンドで体力を計測できたサンプル率
- 既存フィールドは変更なし（後方互換）

`round_stats.parquet` の追加列:

| 列 | 内容 |
|----|------|
| `healthMin` / `healthAvg` / `healthEnd` | ラウンド内の最小・時間重み付き平均・最終体力（％） |

`schema/character_health.json`（新規・単一ソース）:

```json
{
  "$schema": "./character_health.schema.json",
  "description": "SF6 キャラクター別の最大体力（ADR-050）。表記は config/character_aliases.json の正規名に合わせる",
  "default": 10000,
  "characters": {
    "GOUKI": 9000,
    "MARISA": 10500,
    "E.HONDA": 10500,
    "ALEX": 10500,
    "ZANGIEF": 11000
  }
}
```

検証結果（1試合 2 ラウンド）:

| ラウンド | サイド | 開始時 | 終了時 | healthMin | healthAvg | healthCoverage |
|---------|--------|--------|--------|-----------|-----------|---------------|
| R1 | 1P | 99.7% | 23.6% | 3.3 | 43.3 | 0.97 |
| R1 | 2P | 99.0% | 59.7% | 36.8 | 73.8 | 0.98 |
| R2 | 1P | 99.1% | 4.2%（K.O.） | 1.0 | 37.1 | 0.91 |
| R2 | 2P | 98.7% | 31.0% | 13.3 | 56.4 | 0.91 |

追加確認: `JzKWGcwFt2w` の先頭 300 秒（13 試合中の前半）でも、ラウンド先頭の体力は平均 99.3%、
最小 1.1%（K.O.）、最大 100.0% となり、他動画でも同様に計測できていることを確認した。

手元 3 本への適用結果:

| 動画 | 長さ | 試合 | 体力イベント | ラウンド先頭の平均 | 最小 / 最大 | healthCoverage 平均 |
|------|------|------|-------------|-------------------|-------------|---------------------|
| `DSgD_bQhxp0` | 2953s | 21 | （先頭 145 秒で検証） | 99.1% | 1.1% / 100.0% | 0.91〜0.98（先頭 2 試合） |
| `JzKWGcwFt2w` | 1866s | 13 | 1779 | 98.5% | 1.0% / 100.0% | 0.80 |
| `Ndwu08Q--_M` | 1956s | 13 | 1285 | 98.1% | 1.0% / 100.0% | 0.77 |

全動画でラウンド先頭はほぼ満タン、最小は K.O. 相当の 1% 前後となり、`round_stats` の
体力集計列（`healthMin` / `healthAvg` / `healthEnd`）も全ラウンドで出力されている。

実装時に判明した事項（ADR の決定を補足）:

- **ラウンド開始のバー伸長演出**: 最初の約 1 秒は 40〜50% から満タンへ伸びる演出値が計測される。
  `health_warmup_sec = 1.5` と `health_start_min_percent = 99` で計測開始を遅らせて除外する
- **急な増加は計測ノイズ**: 回復は回復可能ダメージの自然回復（実測で約 0.2〜5%/秒）しかありえないため、
  `health_max_increase_per_sec = 5.0` を超える増加は前値を保持して除去する（K.O. のドレインによる減少は制限しない）
- **キャリブレーション**: 満タン時の実測値が 1P ≈ 93.6% / 2P ≈ 98.3% と系統的に低く出るため、
  `calibration.health_fill_scale`（1P 1.07 / 2P 1.02）で補正した。補正後はラウンド開始が 98.7〜99.7% になる
- **K.O. のドレイン**: K.O. 後にバーが 0 へ向けて急速に減る。減少方向は制限していないため、
  ラウンド終端の数秒は「演出を含む値」として記録される（内容は自然に読めるため仕様とした）
- **計測精度**: 満タン付近の補正後誤差は ±2% 程度。回復可能ダメージの自然回復で値が緩やかに増加する
  （これは実ゲームの振る舞いであり、現在体力には回復可能分が含まれていないため誤りではない）
