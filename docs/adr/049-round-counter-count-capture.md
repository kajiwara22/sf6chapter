# ADR-049: ラウンド単位のカウンター・パニッシュカウンター回数取得

## ステータス

採用 - 2026-10-10（実装完了）

## 文脈

### 要望

SF6 の対戦動画から、**カウンター（COUNTER）とパニッシュカウンター（PUNISH COUNTER）が
1P サイド / 2P サイドそれぞれで、ラウンドごとに何回発生したか**を確認できるようにしたい。

- 単位は「ラウンドごと」「1P/2P サイド別」
- 「誰が決めたか」が分かればよい（ダメージ量・コンボ内容までは不要）

例（要望の元になったシーン）: `https://youtu.be/DSgD_bQhxp0?t=45` — 1P サイドのパニッシュカウンター。

### 現状のデータでは不足

| データ | 取得できるもの | カウンター情報 |
|--------|--------------|--------------|
| `matches.parquet`（動画解析） | startTime, 1P/2P キャラ, 勝敗 | なし |
| `battlelog_replays.parquet`（ADR-020/031/037） | replay_id, uploaded_at, キャラ, LP/MR, `round_results` | **なし** |
| `chapters.json` / `videos/{id}.json` | チャプター（試合開始時刻・キャラ・勝者） | なし |

Battlelog API はカウンター回数を返さない。**動画フレームを解析する以外に入手手段がない。**

またラウンド単位の情報は Battlelog の `round_results`（ラウンド数と勝敗）だけで、
**ラウンドの開始・終了時刻は動画側からしか取れない**。この課題は ADR-048 で解決する
（`round_splitter.py` による ROUND バナー・K.O. 検出）。本 ADR はその成果を前提にし、
**ラウンド境界の検討は繰り返さない。**

### 実動画での実測（本 ADR の根拠）

対象: `packages/local/download/20261006[DSgD_bQhxp0].mp4`（1920x1080 / 60fps / 2953 秒）
手法: 固定 ROI を切り出し、OpenCV のグレースケールテンプレートマッチング（`TM_CCOEFF_NORMED`）で判定

#### 判明したバナー仕様（1080p 基準の実測値）

| 要素 | COUNTER | PUNISH COUNTER |
|------|---------|----------------|
| 表示位置 (y) | 478〜528 | 478〜528（同じ） |
| 左（1P）の文字 | x ≈ 55 から左寄せ | x ≈ 55 から左寄せ |
| 右（2P）の文字 | x ≈ 1868 で右寄せ | x ≈ 1890 付近で右寄せ |
| 文字の高さ | 約 30px | 約 30px |
| 見た目 | 細い黄バー＋白文字 | 太いオレンジのリボン＋白文字 |
| 持続時間 | 中央値 1.7 秒 | 中央値 1.7 秒 |

判明したドメインルール:

- **バナーは「カウンターを決めた側（attacker）」に表示される**（実測で確認）
  - t=45: 1P の JP が GOUKI をパニッシュ → 左に表示
  - t=1326: 2P の GOUKI が ZANGIEF を K.O.（パニッシュ） → 右に表示
- 再トリガーすると連続表示される（空白 0.3〜0.5 秒を挟んで再表示。実測最長 6.7 秒）
- バナー種別ごとにテンプレートを分けないと判別できない
  - PUNISH COUNTER 用テンプレートは COUNTER バナーにマッチしない（スコア 0.38）
  - COUNTER 用テンプレートは PUNISH COUNTER バナーにマッチしない（スコア 0.22）

#### 検出精度（切り出し画像の目視検証）

| 種別 | 左（1P） | 右（2P） | 誤検出（目視） |
|------|---------|---------|--------------|
| PUNISH COUNTER | 54 件 | 80 件 | 0 件 |
| COUNTER | 97 件 | 116 件 | 0 件 |

- マッチスコアの分離: 陽性フレーム 0.85〜1.0 / 非該当フレーム ≤ 0.46（閾値 0.7 で十分な余裕）
- 50 分の動画で合計 約 350 件（1 試合あたり 20 件前後）
- 上表は壁打ち時点の暫定値（クラスタリングの空白幅 0.6 秒）。実装後の再計測値は下の「実装後の全編検証」を参照

#### コスト実測（同一環境）

| 項目 | 実測 |
|------|------|
| シーケンシャルデコード | 480 fps（1080p60。50 分動画で約 6 分。ADR-048 の実測と一致） |
| カウンター判定（両サイド 2 テンプレート / 10〜15Hz） | 約 0.5 ms/マッチ → 50 分動画で 1〜2 分（デコードの 1〜5%） |

#### 実装後の全編検証（2026-10-10）

`scripts/analyze_counters.py` で同動画の全編（2953 秒 / 42 ラウンド）を再計測した結果。
検証用に独立実装した全編スキャン（今回の壁打ちで使用したスクリプト）と件数が完全に一致した。

| 種別 | 左（1P） | 右（2P） |
|------|---------|---------|
| PUNISH COUNTER | 55 件 | 84 件 |
| COUNTER | 101 件 | 129 件 |
| 合計 | 156 件 | 213 件（全体 369 件） |

- `min_duration_sec = 0.4` 適用後の件数。短時間の検出（< 1.0 秒）は 5 件あり、
  いずれも目視確認の結果「再トリガーで種別が切り替わった区間」（例: 60.8〜61.2 秒の
  PUNISH COUNTER → 61.4 秒以降 COUNTER）または動画末尾での切断であり、誤検出ではなかった
- 検出した全件のバナー切り出し画像を目視確認（閾値 0.7 での誤検出は 0 件）
- 処理時間 450 秒（デコード律速。ADR-048 のゲージ計測と同一ループで実行）
- `round_stats_preview.json` は 84 行（42 ラウンド × 2 サイド）で、
  ADR-048 のゲージ列とカウンター列が同じ行に並ぶことを確認

## 決定

### 1. 計測手法は固定 ROI のテンプレートマッチング（学習モデル・VLM は使わない）

- バナーは文字も位置も固定であり、決定論的に読める（ADR-026 / ADR-048 と同じ手法）
- テンプレートは**種別 × サイド**で用意する
  - `template/counter/`: `counter_left.png` / `counter_right.png` / `punish_left.png` / `punish_right.png`
  - 閾値はマッチスコア 0.7 を初期値とし、目視検証で調整する
- 判別ルール: PUNISH テンプレートが閾値超なら PUNISH COUNTER、そうでなく COUNTER テンプレートが
  閾値超なら COUNTER（同時に超えた場合はスコアが大きい方。実測では混在は再トリガー境界のみ）

### 2. 収録対象は COUNTER と PUNISH COUNTER のみ

- ドライブリバーサル等の他コールアウトは本 ADR のスコープ外（必要になったら別 ADR）
- 同位置に出る他テキストは、テンプレートが一致しない限り検出しない

### 3. サイド判定は「バナーが出た側＝カウンターを決めた側」とする

- 左 = 1P サイド、右 = 2P サイドとして `side` を記録する
- 生データは 1P/2P のみ保持し、自分視点への変換は Web 側で行う（ADR-030/046 の `MY_PLAYER_ID` 判定）

### 4. 「1 回」の定義は ON 区間の分離で行う（空白 0.25 秒以上で別カウント）

- マッチスコアが閾値を超えた区間（ON 区間）を数える
- 空白 0.25 秒以上で別のカウンター、0.13 秒程度の瞬断は同一バナーの検出ゆらぎとして連結する
- 閾値・空白・最小表示時間は `config/detection_params.json` のカウンター用プロファイルで管理し、
  目視検証でチューニングする（ADR-017 の方針）

### 5. 計測は ADR-048 のサンプリングフックに相乗りする（別パスを作らない）

`TemplateMatcher.detect_matches()` は動画を 1 回シーケンシャルにデコードしている。
ADR-048 で追加するフックにカウンター判定も載せ、**同じデコード結果を使う。**

- サンプリング間隔: ADR-048 と同じ 0.1 秒（6 フレーム）
- 追加コストはデコードの 1〜5%（決定1 の実測）

### 6. ラウンド境界は ADR-048 の `round_splitter` を利用する

- 本 ADR ではラウンド境界の検出手法を再検討しない
- ADR-048 の「ラウンド検出数と Battlelog `round_results` の突合」の結果をそのまま使う
- ラウンド境界が確定できなかった試合（ROUND バナー未検出）は、ADR-048 が生成する
  「試合全体を 1 ラウンドとして扱う行」にカウンター回数を集計する。この行は
  `bannerDetected = false` とラウンド数不一致フラグで識別できる（サイレントに誤割当しない）

### 7. 保存は `round_stats.parquet` に列を追加する

ADR-048 で新設する `round_stats.parquet`（1 行 = 1 ラウンド × 1 サイド）に列を足す。
新しいテーブルや `matches.parquet` の肥大化は行わない。

| 追加列 | 型 | 説明 |
|--------|----|------|
| `counter_count` | int | そのラウンド・サイドが決めた COUNTER の回数 |
| `punish_counter_count` | int | そのラウンド・サイドが決めた PUNISH COUNTER の回数 |

試合合計・ラウンド別合計は UI / クエリ側で `SUM` して導出する（生データに持たない）。

### 8. カウンター発生時刻は保存しない

本 ADR のスコープは回数のみとする。YouTube の該当シーンへのディープリンクが必要になった
場合は、ADR-048 の `gauges/{match_id}.json` に発生時刻列を足す形で別途拡張する。
（検証用の中間ファイルには ON 区間を記録するため、後から回数を再計算できる）

### 9. Web 表示はラウンドバッジへの併記と詳細パネルの両方

- 対戦履歴ページ（ADR-034/047）のラウンド結果バッジ（V/C/SA…）に、カウンター件数を併記する
- ADR-048 のラウンド別詳細パネル内にも、1P/2P のカウンター数を表示する
- 自分視点への変換は ADR-047 と同様に UI 側で行い、Battlelog 未マッチの試合は 1P/2P 表示のみ

### 10. バックフィルは ADR-048 と同じ方針

- 新規動画は本線パイプラインで自動的に計測する
- 既存動画は `download/` に残っている動画を `scripts/analyze_counters.py --video-id <id>`
  （ADR-048 の再処理 CLI と同じ走査に相乗り）で順次再処理する
- 全件バックフィル（YouTube 再ダウンロード）は行わない

### 11. 検証用の中間ファイルを保存する

ADR-011/018/048 の方針に合わせ、`./intermediate/{video_id}/counters/` に
**検出したバナーの切り出し画像**と **ON 区間の時系列 CSV** を出力し、目視で誤検出・数え方を
確認できるようにする。Battlelog にはカウンター情報がないため、突合による自動検証はできない
（この点が ADR-026/048 と異なる）。

## 選択肢の比較

### 計測手法

| 手法 | 精度 | コスト | 実装/保守 | 判定 |
|------|------|--------|----------|------|
| A. 固定 ROI + テンプレートマッチ | ◎ 表示そのものを読む（実測 誤検出 約1%） | ◎ デコードの 1〜5% | ○ 座標キャリブレーションが必要 | **採用** |
| B. 小型 CNN の画像分類 | ◎（学習次第） | △ 学習データ整備・推論 | △ モデル管理が増える | 不採用 |
| C. Gemini 等 VLM でフレーム画像を読む | △ 回数のブレ・幻覚 | ✕ 数千フレームで高コスト | △ プロンプト管理 | 不採用 |
| D. Battlelog API から取得 | — | — | — | **不可（データが存在しない）** |

VLM を使わない理由: カウンターは「決まった瞬間に固定文言のバナーが出る」という決定論的な
情報であり、ピクセル判定のほうが安価・高速・再現可能。既存パイプラインも VLM はキャラクター名
認識のみに限定している（ADR-019/042）。

### 収録対象

| 方式 | 価値 | コスト/リスク | 判定 |
|------|------|--------------|------|
| A. COUNTER + PUNISH COUNTER のみ | 要望そのもの | 小 | **採用** |
| B. REVERSAL 等の他コールアウトも同時に収録 | △ 将来使うか不明 | テンプレート・目視検証が増える | 不採用（別 ADR で） |

### 「1 回」の定義

| 方式 | 長所 | 短所 | 判定 |
|------|------|------|------|
| A. 空白 0.25 秒以上で別カウント | 実測の瞬断（0.13 秒）と再トリガー（0.3〜0.5 秒）を分離できる | 閾値が経験値 | **採用（目視で調整）** |
| B. 空白 0.5 秒以上で別カウント | 保守的（少なめに数える） | 連続再トリガーを取りこぼす | 次点 |
| C. ON 区間の合計時間 ÷ 1.7 秒で推定 | 空白に依存しない | K.O. 等でバナーが短縮されると過小評価 | 不採用 |
| D. 「発生あり/なし」のみ | 曖昧さゼロ | 要望（回数）を満たさない | 不採用 |

### 保存先

| 方式 | 検索・集計 | 詳細表示 | 影響範囲 | 判定 |
|------|-----------|---------|---------|------|
| A. `round_stats.parquet` に列追加 | ◎ | ○ | 小 | **採用** |
| B. `round_counters.parquet` を新設 | ◎ | ◎ | 小（テーブル数が増える） | 次点 |
| C. `matches.parquet` に列追加 | ◎ | △ | 全クエリに影響 | 不採用 |
| D. `gauges/{match_id}.json` にのみ保存 | ✕ | ◎ | 小 | 不採用（検索できない） |

## リスクと対策

| リスク | 内容 | 対策 |
|--------|------|------|
| 連続再トリガーの数え方 | 同一バナーの検出ゆらぎと、実際の連続カウンターを誤って同一視／分離する | 空白閾値 0.25 秒を初期値とし、中間ファイルの ON 区間（最長 6.7 秒の例など）を目視して調整。ON 区間を保存するので**後から再計算できる** |
| 検証ソースが無い | Battlelog にカウンター情報がないため、勝敗・ラウンド数のような突合検証ができない | バナー切り出し画像を全件出力し、目視で全数確認する運用（実測ではこの方法で誤検出 約1% を確認） |
| 他コールアウトの混入 | 同位置に REVERSAL 等が出た場合、誤検出しうる | 種別ごとのテンプレートで判別し、閾値を 0.7 に設定。実測では COUNTER / PUNISH COUNTER 以外の混入は無し。スコア分布を中間ファイルに残して監視 |
| PUNISH / COUNTER の相互誤判定 | 再トリガー境界で両テンプレートが同時に反応する | 同時に閾値超の場合はスコアが大きい方を採用。境界の扱いを中間ファイルで目視確認 |
| HUD バージョン差 | 過去に HUD が変わっている（`round1_2026_new_monitor.png` の命名） | 座標は 1080p 正規化＋バナーをテンプレートで検出。座標・閾値は `config/detection_params.json` のプロファイルで管理 |
| 解像度・クロップ差 | 将来 720p やレターボックス配信があると固定座標がずれる | ADR-048 と同じ正規化＋アンカー検出。検出失敗時は「未計測」として記録し、サイレントに誤値を出さない |
| ラウンド未確定 | `round_splitter` がラウンド境界を取れない試合がある | ADR-048 が生成する「試合全体を 1 ラウンドとして扱う行」に集計し、`bannerDetected = false` とラウンド数不一致フラグで識別できるようにする（決定6） |
| ラウンド終端の短縮表示 | K.O. 演出中にバナーが出ると表示が短く、数え漏らす可能性 | 最小表示時間（初期値 0.4 秒）を閾値管理し、中間ファイルで確認 |
| 既存動画の再処理コスト | 動画ファイルは `download/` に全件残っていない | ADR-048 と同じく新規＋手元の動画のみ。`--video-id` 指定の再処理 CLI を用意 |
| ADR-048 への依存 | `round_splitter` 未実装の間はラウンド単位の集計ができない | 実装順は ADR-048 → 本 ADR。先行実装する場合は試合単位の集計のみ（列は同じ） |

## データモデル

`round_stats.parquet`（ADR-048 で新設。本 ADR で **太字の 2 列を追加**。ゲージ系の列は省略して記載）

列名は ADR-048 の実装に合わせて camelCase とする。

| 列 | 型 | 説明 |
|----|----|------|
| `match_id` | string | 対戦 ID（`video_id_startTime`） |
| `video_id` | string | YouTube 動画 ID |
| `round` | int \| null | ラウンド番号（1〜3）。確定できない場合は null |
| `side` | string | `player1` / `player2` |
| `character` | string | キャラクター名（正規化済み） |
| `round_start_time` | float | ラウンド開始（動画内秒） |
| `round_end_time` | float | ラウンド終了（動画内秒） |
| `detection_confidence` | float | 検出信頼度（ラウンド境界＋カウンター検出） |
| **`counterCount`** | int \| null | そのラウンド・サイドが決めた COUNTER 回数（未計測時は null） |
| **`punishCounterCount`** | int \| null | そのラウンド・サイドが決めた PUNISH COUNTER 回数（未計測時は null） |

中間ファイル `intermediate/{video_id}/counters/`（検証・再計算用）

- `counters.json`: ラウンド別の回数と ON 区間
- `counters_samples.csv`: 全サンプルのスコア時系列（`timestamp, side, counter_score, punish_counter_score, active_type`）
- `banners/*.png`: カウンター開始時点のバナー切り出し画像（目視確認用、最大 80 枚）

```json
{
  "videoId": "DSgD_bQhxp0",
  "roundBannerTimes": [21.0, 72.25],
  "matches": {
    "DSgD_bQhxp0_20": {
      "matchId": "DSgD_bQhxp0_20",
      "rounds": [
        {
          "round": 1,
          "roundStartTime": 21.0,
          "roundEndTime": 72.25,
          "endReason": "next_round",
          "bannerDetected": true,
          "player1": {
            "counterCount": 2,
            "punishCounterCount": 1,
            "occurrences": [
              { "type": "punish_counter", "side": "player1", "start": 45.27, "end": 47.0, "peakScore": 0.961 }
            ]
          },
          "player2": { "counterCount": 1, "punishCounterCount": 4, "occurrences": [] }
        }
      ]
    }
  },
  "occurrences": [
    { "type": "punish_counter", "side": "player1", "start": 45.27, "end": 47.0, "peakScore": 0.961 }
  ]
}
```

- `type`: `counter` | `punish_counter`
- `start` / `end`: マッチスコアが閾値を超えていた区間（動画内絶対秒）。空白 `merge_gap_sec` 未満は連結済み
- `occurrences` は中間ファイル専用で、parquet には `counterCount` / `punishCounterCount` だけを保存する（決定8）

## 実装メモ（実装時に確定した事項）

| 項目 | 実装 |
|------|------|
| テンプレート | 種別×サイドの 4 枚。PUNISH COUNTER は全文、COUNTER も全文を照合し、閾値超のうちスコアが大きい方を採用 |
| ON 区間のピークスコア | ON 区間内の最大スコアを `peakScore` として中間ファイルに保持（parquet には保存しない） |
| ラウンドへの割り当て | ON 区間の**開始時刻**で割り当てる（境界をまたぐ二重カウントを回避）。バナー未検出の第1ラウンド（試合開始時刻を代用）に限り 0.5 秒の許容幅を持たせる |
| `round_stats` 行の生成元 | ADR-048 の `build_round_stats_rows()` に相乗り。ラウンド×サイド行はゲージ計測が生成し、そこにカウンター列をマージする。ゲージ計測を無効にした場合は行自体が生成されない（ADR-048 が前提という決定6の帰結） |
| 未計測の表現 | カウンター未計測（計測無効・試合が対象外）は `null`、計測済みで 0 件は `0`。Web の詳細パネルでも `-` と `0` を区別する |
| Web（一覧） | 履歴行のラウンドバッジ各に `C2 PC1` のように併記。`myRounds`/`oppRounds` の添字＝ラウンド番号で対応付ける。round_results が無い行でもビデオ側の回数だけを表示する |
| Web（詳細） | ラウンド集計テーブルに「カウンタ」「パニッシュ」列を追加 |
| 旧 Parquet 対応 | round_stats にカウンター列が無い場合は列を参照せずに問い合わせる（ADR-048 の表示を壊さない） |
| 検証方法 | `analyze_counters.py` が出力するバナー切り出し画像と ON 区間 CSV を目視確認。独立に実装した全編スキャンスクリプトと件数が一致することを確認 |
