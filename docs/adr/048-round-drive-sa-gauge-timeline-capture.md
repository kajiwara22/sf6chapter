# ADR-048: ラウンド単位のドライブゲージ・SAゲージ時系列取得

## ステータス

採用 - 2026-10-10（実装完了 2026-10-10）

## 文脈

### 要望

SF6 の対戦動画から、**ラウンド内でドライブゲージ・SAゲージがどう変動したか**を 1P サイド / 2P サイドそれぞれについて確認できるようにしたい。

- 粒度はドライブゲージ 0〜6 本、SAゲージ 0〜3 本で十分（それ以上の詳細値は不要）
- ドライブゲージは**バーンアウトだった期間**が取れると嬉しい
- 単位は「ラウンドごと」「1P/2Pサイド別」

### 現状のデータでは不足

| データ | 取得できるもの | ゲージ情報 |
|--------|--------------|-----------|
| `matches.parquet`（動画解析） | startTime, 1P/2P キャラ, 勝敗 | なし |
| `battlelog_replays.parquet`（ADR-020/031/037） | replay_id, uploaded_at, キャラ, LP/MR, `round_results` | **なし** |
| `chapters.json` / `videos/{id}.json` | チャプター（試合開始時刻・キャラ・勝者） | なし |

`scripts/convert_battlelog_to_parquet.py` のスキーマにゲージ系カラムは存在せず、Battlelog API もゲージ推移は返さない。
**動画フレームを解析する以外に入手手段がない。**

また、ラウンド単位の情報は Battlelog の `round_results`（ラウンド数と勝敗）だけであり、
**ラウンドの開始・終了時刻は動画側からしか取れない**。

### 実動画での実測（本 ADR の根拠）

対象: `packages/local/download/20261006[DSgD_bQhxp0].mp4`（1920x1080 / 60fps / 2953 秒）
手法: ffmpeg でフレームを抽出し、OpenCV で ROI の HSV 統計とテンプレートマッチングを計測

#### 判明した HUD 仕様（1080p 基準の実測値）

| 21.0 | （ROUND バナー検出） | — | ラウンド開始 |

この結果から確認できたドメインルール（計測の整合性チェックに使える）:

- SA ゲージ: **表示数字＝ストック数（0〜3）**、バーは次ストックへの進捗で、ストック獲得時にリセットされる
- SA ゲージ: **低体力かつ 3 ストックのとき、表示が「3」から「CA」に変わる**（CA はストック 3 と同義）
- SA ゲージは**ラウンド間で持ち越し**、マッチ開始で 0 にリセット
- ドライブゲージは**ラウンドごとに満タンへリセット**

#### コスト実測（同一環境）

| 項目 | 実測 |
|------|------|
| シーケンシャルデコード（1080p60） | 約 480 fps（2.1 ms/フレーム） |
| ゲージ解析込みの単独パス | 145 秒の動画を 17.1 秒（約 8.5 倍速）→ 解析分はデコード比で数 % |
| 既存検出パスへの相乗り | 動画の再デコードが不要。追加はサンプリング処理のみ |

## 決定

### 1. 計測手法は ROI ピクセル解析＋数字テンプレートマッチング（学習モデル・VLM は使わない）

- ドライブゲージ: ROI を 6 等分し、黄緑（通常ゲージ）の充填列数から 0〜6 を算出
- SAゲージ: ゲームが表示している**グリフ 0〜3 と CA をテンプレートマッチで読む**（`round1_2026_new_monitor.png` の "1" 検出と同じ手法）
  - CA はストック 3 として扱い、`saCriticalArt` 期間として区別する
- バーンアウト: **HUD 表示中に黄緑のゲージが検出できない状態**をバーンアウトと判定する
  （銀／赤の回復バーは色の閾値だけでは背景（ステージの赤旗等）と分離しづらいため、
  「SA の数字が読める＝HUD 表示中」を前提条件にした判定のほうが安定する）
  - 単発の誤検出を除くため、最小継続時間（既定 1.0 秒）と近接区間の結合を行う
- SA の数字が読めていることを **HUD 表示判定**にも使う（ラウンド移行・演出中は数字も消える）

### 2. 計測は既存の検出パスに相乗りする（別パスを作らない）

`TemplateMatcher.detect_matches()` は動画を 1 回シーケンシャルにデコードしている。
このループに `GaugeAnalyzer.feed()` をフックし、**同じデコード結果を使う**。

- ゲージ: 既定 0.1 秒間隔（6 フレーム）
- ROUND バナー: 既定 0.25 秒間隔（0.5 倍縮小画像で照合。バナーは約 1.5 秒表示されるため十分）
- 追加コストはデコード比で数 %。別パスにするとデコードが二重になり約 2 倍かかる
  （既存動画のバックフィル用には `scripts/analyze_gauges.py` の単独パスを用意する）

### 3. 記録は「変化点イベント方式」

同一値が連続する区間は畳み、チャンネルごと（ドライブ / SAストック / SAバー進捗）に値が変わった時刻だけを記録する。
1 ラウンドあたりドライブ 5〜40 件、SA ストック 1〜5 件程度で、全フレーム保存に比べ桁違いに小さい。

- ドライブは 0.1 刻みで保持（イベント化の閾値は既定 0.3。±0.15 程度の計測ノイズを吸収する）
- メディアン平滑化（既定 7 点）と短い欠損（既定 1.0 秒以内）の補完を行う

### 4. ラウンド境界は ROUND バナー検出を主、Battlelog で検証

- ラウンド開始: 「ROUND」文字の**テンプレートマッチ**（ROUND 1 / ROUND 2 / FINAL ROUND で共通の文字列）
- ラウンド終端: 次のラウンド開始（最終ラウンドは試合終端）。ゲージの変化点は境界時刻で切り分ける
- 試合終端の手前 3 秒以内のバナーは**次試合の ROUND 1** とみなして除外する
  （次試合のバナーは次試合の検出時刻よりわずかに手前に現れるため、全動画検証で幻のラウンドが発生した）
- ラウンドの実測範囲は **HUD が表示されていた区間**（`visibleFrom` / `visibleTo`）で表現する
- `round_results` のラウンド数と突合し、不一致は警告＋フラグ（誤検出の検知）

FIGHT / K.O. のバナーはテンプレートを作成したが**採用しなかった**。実測すると両者は描画アニメーションが速く
（同一テンプレートが一致するのは 1 フレームのみで、0.1 秒後にはスコアが 0.99 → 0.02 に落ちる）、
複数フェーズのテンプレートを揃えても検出が不安定になる。ROUND バナーは表示中スコアが 0.55〜1.0 で安定しており、
ラウンド開始の検出には十分なため、ラウンド終端は HUD 表示の有無から求める方式にした。

### 5. 保存形式

- **詳細（変化点列）**: `gauges/{match_id}.json` として R2 に保存し、Web 詳細表示でオンデマンド取得
- **集計（検索・分析用）**: `round_stats.parquet`（1 行 = 1 ラウンド × 1 サイド）を追加
  - 列: `videoId` / `matchId` / `round` / `side` / `character` / `roundStartTime` / `roundEndTime` / `durationSec` / `driveMin` / `driveAvg` / `driveEnd` / `saMax` / `saUsedCount` / `detectionCoverage`
  - バーンアウトの回数・累計秒数は詳細 JSON の期間から後日派生できるため、列を追加しない（壁打ち結果: バーンアウトはフラグ＋期間のみ）
- 検索画面全体で使う `matches.parquet` は肥大化させない
- 既存動画の再処理は `scripts/analyze_gauges.py --video-id <id>` で行う（決定8）

### 6. Web 表示

対戦検索の結果行をクリックした詳細パネルで、ラウンドごとに 1P/2P のドライブ・SA 推移を折れ線（ステップ）チャート表示。YouTube リンク（チャプター時刻）を併記する。
将来、分析需要が高まれば「LP推移」と同様のタブに昇格させる。

自分視点への変換は、Battlelog マッチ結果（`p1_short_id` / `p2_short_id`、ADR-030/046 の `MY_PLAYER_ID` 判定）に基づいて UI 側で行う。
Battlelog 未マッチの試合は 1P/2P 表示のみとし、生データには手を入れない（壁打ち結果: サイドは両方保持）。

### 7. 検証用の中間ファイルを保存する

既存の「中間ファイルで人間が目視確認できる」方針（ADR-011/018）に合わせ、`./intermediate/{video_id}/gauges/` に出力する。

- `gauges.json` — ラウンド単位の変化点
- `gauges_samples.csv` — 全サンプルの生値と判定結果（10Hz）
- `roi/*.png` — ラウンド開始・バーンアウト開始・CA開始・SAストック変化時の ROI クロップ（最大 80 件）
- `round_stats_preview.json` — round_stats の行（R2 無効時はこちらで確認）

### 8. バックフィルは新規動画（本線）→手元の動画（再処理 CLI）の順

- 新規動画は本線パイプライン（決定2 の相乗りフック）で自動的に計測する
- 既存動画は `download/` に残っている直近の動画から `scripts/analyze_gauges.py --video-id <id>` で順次再処理する
- 全件バックフィル（YouTube 再ダウンロード）は行わない。将来必要になった場合は別 ADR とする

## 選択肢の比較

### 計測手法

| 手法 | 精度 | コスト | 実装/保守 | 判定 |
|------|------|--------|----------|------|
| A. ROI ピクセル解析＋テンプレート | ◎ 表示そのものを読む | ◎ 追加数 % | ○ 座標キャリブレーションが必要 | **採用** |
| B. 小型 CNN の画像分類 | ◎（学習次第） | △ 学習データ整備・推論 | △ モデル管理が増える | 不採用 |
| C. Gemini 等 VLM でフレーム画像を読む | △ 数値のブレ・幻覚 | ✕ 数千フレームで高コスト | △ プロンプト管理 | 不採用 |
| D. Battlelog API から取得 | — | — | — | **不可（データが存在しない）** |

VLM を使わない理由: ゲージは「表示されている数字とバーの長さ」という決定論的な情報であり、
ピクセル計測のほうが安価・高速・再現可能。既存パイプラインも VLM はキャラクター名認識のみに限定している（ADR-019/042）。

### サンプリング

| 方式 | 追加コスト | 取りこぼし | 判定 |
|------|-----------|-----------|------|
| 既存デコードに相乗り（10Hz） | デコード比で数 % | ほぼなし（バナーは複数サンプルで捕捉できる） | **採用** |
| 独立スクリプトで再度デコード | 約 2 倍 | なし | バックフィル用 CLI としてのみ用意 |

### 保存形式

| 方式 | 検索・集計 | 詳細表示 | 影響範囲 | 判定 |
|------|-----------|---------|---------|------|
| A. 動画単位 JSON（`gauges/{match_id}.json`） | ✕ | ◎ | 小 | 併用 |
| B. `round_stats.parquet` 新設 | ◎ | △ | 小 | **併用（採用）** |
| C. `matches.parquet` に JSON 列を追加 | △ | ◎ | 全クエリに影響 | 不採用 |
| D. `videos/{id}.json` にネスト | ✕ | ○ | 小 | 次点（B と役割重複） |

## リスクと対策

| リスク | 内容 | 対策 |
|--------|------|------|
| HUD バージョン差 | `round1_2026_new_monitor.png` の命名が示すとおり過去に HUD が変わっている。座標固定だと将来壊れる | 座標は 1080p 正規化（動画解像度から比例拡大）＋テンプレートで `config/detection_params.json` の `gauge_analysis` に集約。将来の HUD 変更時はこのブロックとテンプレートのみ差し替える |
| 解像度・クロップ差 | 将来 720p やレターボックス配信があると固定座標がずれる | 上記の正規化。計測不能時は `detectionCoverage` が下がるので検知できる |
| SA 数字の未知グリフ | 実測で「3」はテンプレート未所持時に低スコアになった（CA も同様） | 0〜3 と **CA** の 5 テンプレートを用意。閾値未満は「HUD 非表示」として扱い、欠損を補間する |
| CA は 2 文字で幅が広い | 数字 1 文字分の ROI では CA が切れる | CA を含む広めの探索窓（x 55〜185）でサーチマッチする |
| 演出中の HUD 非表示 | スーパー演出・K.O. 演出・ラウンド移行ではゲージが描画されない（実測で SA 数字のスコアが 0.00 になる） | HUD 非表示として扱い、前後 1.0 秒以内の欠損のみ補完。長い欠損は欠損のまま（勝手に補間しない） |
| バーンアウト判定の誤検出 | 演出中などに黄緑が消えるとバーンアウトと誤認しうる | HUD 表示中を前提条件にし、最小継続時間 1.0 秒と近区間の結合で単発の誤検出を除外 |
| ドライブ本数の系統誤差 | ゲージ外側の斜めの先端は充填列の判定から漏れ、満タン時に約 0.2〜0.3 本低く出る | 実測に基づき外側の先端を ROI から除外（1P: x574〜880、2P: x1040〜1346）。残差は `calibration.drive_fill_scale` で補正可能 |
| 計測ノイズ | 満タン付近で ±0.15 程度、演出中は ±0.5 を超える外れ値が出る | メディアン平滑化（7 点）＋イベント閾値（0.3）＋短い欠損の補完 |
| ラウンド境界の誤検出 | ROUND バナーが取れないとラウンドが分割できない | バナー未検出時は「試合開始＝第1ラウンド」としてフォールバックし、`bannerDetected=false` を記録。Battlelog `round_results` と突合し `roundCountMatch` に結果を残す |
| 既存動画の再処理コスト | 動画ファイルは `download/` に全件残っていない | 新規動画のみ本線で計測し、手元の動画は CLI で再処理（決定8） |

## データモデル

`gauges/{match_id}.json`（R2）:

```json
{
  "videoId": "4clVjHemKs0",
  "matchId": "4clVjHemKs0_166",
  "detectedRoundCount": 2,
  "battlelogRoundCount": 2,
  "roundCountMatch": true,
  "rounds": [
    {
      "round": 1,
      "roundStartTime": 21.0,
      "roundEndTime": 72.25,
      "endReason": "next_round",
      "bannerDetected": true,
      "player1": {
        "visibleFrom": 0.57,
        "visibleTo": 50.3,
        "coverage": 0.958,
        "drive": [[0.57, 5.88], [3.03, 5.16], [12.03, 0.0]],
        "driveBurnout": [[12.03, 50.18]],
        "sa": [[0.78, 0], [22.32, 1], [47.4, 2]],
        "saProgress": [[0.78, 0.0], [22.2, 0.98]],
        "saCriticalArt": []
      },
      "player2": { "...": "同構造" }
    }
  ]
}
```

- `drive`: `[ラウンド開始からの経過秒, 本数(0〜6, 小数1桁)]` の変化点列
- `sa`: `[経過秒, ストック(0〜3, 整数)]` の変化点列（表示数字を正とする）
- `driveBurnout` / `saCriticalArt`: 期間の `[開始経過秒, 終了経過秒]`
- `saProgress`: 参考値（次ストックへの進捗 0〜1）
- `coverage`: ラウンド内でドライブを計測できたサンプル率（1.0 に近いほど良好）

`round_stats.parquet`（1 行 = 1 ラウンド × 1 サイド）:

| 列 | 内容 |
|----|------|
| `videoId` / `matchId` | 試合の識別子（`matches.parquet` と同じ `videoId` で置換更新する） |
| `round` / `side` / `character` | ラウンド番号・サイド・キャラクター名 |
| `roundStartTime` / `roundEndTime` / `durationSec` | HUD 表示区間の絶対時刻（秒）と長さ |
| `driveMin` / `driveAvg` / `driveEnd` | ドライブ本数の最小・時間重み付き平均・最終値 |
| `saMax` / `saUsedCount` | 到達した最大ストック数・ストックが減少した回数（スーパー使用の目安） |
| `detectionCoverage` | 計測できたサンプル率 |

- バーンアウト期間・CA 期間も全動画で検出（合計 163/26、115/23、94/16）

実データ検証で見つけて修正した問題:

1. **幻のラウンド**: 次試合の ROUND 1 バナーが現試合の末尾（次試合の検出時刻より手前）に入り、coverage 0 のラウンドが生成されていた。`TRAILING_BANNER_MARGIN_SEC = 3.0` で試合終端手前のバナーを除外して修正
2. **HUD 可視判定のちらつき**: SA 数字のマッチスコアが閾値付近で揺れると 0.1 秒単位で HUD 非表示と判定され、ドライブが欠損していた。`hud_flicker_tolerance_sec = 0.5` で短い途切れを表示中に丸めて修正（`DSgD_bQhxp0` の coverage mean 0.80 → 0.84、min 0.15 → 0.39）
3. **バナー閾値の不足**: `JzKWGcwFt2w` の試合開始バナーがスコア 0.397（閾値 0.40 未満）で取りこぼされ、第1ラウンドのみの試合が発生。`round_banner_threshold` を 0.35 に下げて修正（他の 2 本の検出数は不変。負例のスコアは 0.13 以下なので誤検出の余地はない）
4. **代用ラウンドのフラグ漏れ**: 第1ラウンドのバナーを取りこぼしたときに試合開始時刻を代用したラウンドを `bannerDetected=true` と誤記していた。`bannerDetected=false` を返すよう修正
5. **SA 数字 ROI の余裕不足**: 数字グリフの上下に対して探索領域の余裕が 10px しかなく、スコアが不安定だった。ROI を `x 45〜195 / y 938〜1075` に広げて余裕を確保（`Ndwu08Q--_M` の coverage min 0.13 → 0.14、mean 0.85 → 0.86）

既知の制約:

- ドライブ本数は満タン付近で ±0.2 程度の系統誤差が残る（表示は 0〜6 の段単位なので実用上は問題なし）
- ラウンド終端は K.O. 時刻そのものではなく、HUD が消える時刻（K.O. 演出終了）になる
- `round_stats.parquet` の `character` は試合データから埋めるため、`matches` に存在しない試合では null になる
- **ラウンド分割は既存の試合検出に依存する**: 既存パイプラインが 1 試合を 2 つに分割して検出した場合、前側の試合が 1 ラウンドになる（実測: `Ndwu08Q--_M` の 1027.83s。1031.0s の ROUND 2 が新規試合として扱われた）。この場合は Battlelog の `round_results` との突合で `roundCountMatch=false` になるので検知可能。根本対応は試合検出側（別 ADR）
- Web 側はユニットテスト（`pnpm test` 112 件）と `pnpm typecheck` / `pnpm build` のみ確認済みで、**R2 に実データを置いた状態での描画確認は未実施**
- 動画の 1P/2P と Battlelog の p1/p2 の対応（自分視点変換）は実データで未確認（キャラクター名一致を優先し、判別不能時は 1P/2P 表示）
